## Support windows of the platform

The wiki stands on two release lines with end dates; plan the move to the next before them.

| Component | Line | Security fixes until |
| --- | --- | --- |
| MediaWiki | 1.43 (LTS) | December 2027 |
| PHP | 8.3 | 31 December 2027 |

The container's PHP comes with the MediaWiki image; the offline viewer's PHP is pinned in `offline/php/build.zig.zon`. Both move together, and with them Semantic MediaWiki, Wikibase (whose branch follows MediaWiki's) and ICU.

## Pins of the wiki service's image

The `Dockerfile` pins the MediaWiki and Composer images by digest, Wikibase by commit, and the Debian packages it installs by a snapshot of Debian's archive (`DEBIAN_SNAPSHOT`, at or after the MediaWiki image's build); `composer/composer.lock` pins every Composer package. `image/inventory.tsv` lists every Debian package of the built image, its PHP and its PECL extensions; `image/inventory.sh` writes it inside the image. `zig build sbom` reads all of them, so the SBOM follows a change of pin without an edit. README, "Upgrading", has the steps. CI's Server job fails while the lock is missing or the inventory is not what the image holds, and offers a fresh one of each as an artifact (`composer-lock`, `image-inventory`).

## Hand-maintained parts of the offline PHP build

`offline/php` builds PHP and its libraries from pinned official releases. Most of it follows the releases automatically; the parts below are kept by hand and are what to check when a version changes.

### What is automatic

- **Fetching and pinning.** Each release is named by URL and content hash in `offline/php/build.zig.zon`; a changed archive fails the build.
- **Applying patches.** `tools/prepare_src.c` copies the PHP release into the build cache and applies `patches/` there. It is strict: a hunk that does not match exactly fails the build.
- **Fiber assembly.** `tools/masm2gas.c` converts PHP's own Microsoft-syntax routines (`Zend/asm/*_x86_64_ms_pe_masm.asm`) at build time. Nothing converted is kept in the repository. It refuses any directive it does not know.
- **`config.w32.h` and `internal_functions.c`.** `build.zig` generates both from its table of extensions.
- **Header-name spellings.** Generated by `build.zig`.

### What is kept by hand

| Item | Where | Check when |
| --- | --- | --- |
| Versions, URLs and hashes of PHP and every library | `build.zig.zon` | Any version changes. Verify the publisher's checksum or signature before pinning. |
| Patch for building PHP against MinGW-w64 headers (nine files) | `patches/php-8.3-mingw.patch` | PHP changes. Re-base any hunk the build reports as not applying. |
| Patch that lets OPcache run under the embed SAPI (one line) | `patches/php-8.3-opcache-embed.patch` | PHP changes; also if the viewer's SAPI gets a name of its own. |
| Registration of OPcache, which PHP normally loads from a DLL | `test/embed_smoke.c` (later the viewer's host) | PHP changes how Zend extensions start. |
| Lists of PHP source files per extension | `sources.zig` | PHP changes. Compare with `win32/build/config.w32` and each extension's `config.w32`. |
| Per-extension flags, include directories and config defines | the `extensions` table in `build.zig` | PHP changes, or an extension is added. They mirror each extension's `config.w32`; a missing flag can compile and still be wrong (a dropped `HAVE_TIMELIB_CONFIG_H` once corrupted the heap in the date extension). |
| Global compiler flags | `php_flags` in `build.zig` | PHP changes. They mirror `win32/build/confutils.js`. |
| Base configuration defines | `compat/config.base.h` | PHP changes. Compare with what PHP's `configure.js` writes. |
| Stand-ins for headers PHP's Windows build generates | `compat/timelib_config.h`, `compat/wsyslog.h` | PHP changes `ext/date/config.w32` or `win32/build/wsyslog.mc`. |
| POSIX timer functions for LuaSandbox's CPU-time limit, on Win32 | `compat/luasandbox_posix_timers.c` and `.h` | LuaSandbox changes how it uses timers (`timer.c`). |
| Process start-up that PHP's DLL entry point does (clock function, file I/O helpers) | `compat/static_init.inc` | PHP changes `win32/dllmain.c`. A static build never runs `DllMain`, so anything added there must be added here. |
| Source lists, feature switches and config headers of each library | the library functions in `build.zig` | That library changes. Compare with its own build files. |
| What the SBOM says about each component beyond its source and hash: version, license, supplier, published checksum; and the lists of libraries bundled inside PHP and of the wiki software | `components.zig` | Any version changes. The build refuses a dependency with no entry; the bundled and wiki lists are checked by hand. |
| ICU's source file lists | `icu_sources.zig` | ICU changes. Copy from `source/common/sources.txt`, `source/i18n/sources.txt` and `source/io/sources.txt`. |
| The ICU version in the data symbol and file name (`icudt79`) | `icu()` in `build.zig` | ICU changes. |
| The version string of libxml2 | `libxml2()` in `build.zig` | libxml2 changes. |
| Expected test output | `test/smoke.expected`, made by `test/make-expected.sh` | A check is added, or a version it prints changes. |

### On a PHP version change

1. Change the URL and hash in `build.zig.zon`, after checking the release's published checksum.
2. Run `zig build`. Fix what it reports, in this order: patches that no longer apply, source files that moved, directives the fiber converter refuses.
3. Compare the flags and defines in the table above with PHP's Windows build files for the new version.
4. Run the CI workflow `offline-php`; it runs the test script on Windows.

### Known gaps

- The reference for source lists and flags was a build of PHP 8.3.37 made once with Microsoft's compiler. There is no automated comparison against PHP's own build files, so step 3 is by inspection.
- The release signatures (GPG) are not checked by the build; only the content hashes are.
