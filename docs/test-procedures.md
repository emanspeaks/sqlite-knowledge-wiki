# Software test procedures

The test procedures and cases (%[SWE-065]), after handbook topic 5.14. Each is an item of the type `procedure`, `TST-001` and on, linked by `verifies` to the requirements it verifies; its results are recorded with `skein result` or a results file, and summarized in the [test report](test-report.md).

## Results

Both procedures record a result for each check they make, in Skein's TOML results format: `tests/result.sh` appends one, attributed to the test file (`offline/php/test/smoke.php` for TST-001, `tests/server/check.sh` for TST-002), so a result belongs to every requirement that file cites. `tests/smoke.sh` runs TST-001 and records it; `check.sh` records each of its checks when `RESULTS` names a file. CI's Results job gathers a run's results, and `skein coverage --results` gives the requirements they verified; a release publishes both as `test-results.toml` and `coverage.txt`. A result names the implementation `sqlite-knowledge-wiki` and the version in `VERSION`.

## Environment and schedule

Both procedures run in CI (`.github/workflows/ci.yml`) for every pull request into `main` and every push to it, on GitHub's hosted runners: TST-001 on Windows Server 2025 (`windows-2025`), TST-002 on Ubuntu 24.04 with Docker. `tools/agent/check.sh` runs TST-001 locally before a pull request into `dev`.

## Test cases

%procedure[TST-001 integration verifies=SRS-027 verifies=SRS-029 verifies=SRS-031 verifies=SRS-087] The offline viewer's PHP runtime, `offline/php/test/smoke.php`, run by the test program built for Windows (`php-embed-smoke.exe`), in a Debug build and a release build. Each line of its output is one check of an extension or of the engine: Lua called from PHP and back, its memory and CPU-time limits, thumbnails with GD, fibers switched by PHP's own routines, and the rest. It passes when the output is the same as `offline/php/test/smoke.expected`, line for line; the job fails otherwise, and on a crash the program prints a stack trace.

%procedure[TST-002 system verifies=SRS-001 verifies=SRS-002 verifies=SRS-003 verifies=SRS-004 verifies=SRS-005 verifies=SRS-006 verifies=SRS-008 verifies=SRS-009 verifies=SRS-010 verifies=SRS-011 verifies=SRS-032 verifies=SRS-072 verifies=SRS-095] The wiki service, `tests/server/check.sh`, against the image built from the `Dockerfile` and started with `docker compose`: a fresh install (the first run's setup, the admin login), then edits and the queries that must see them (a Semantic MediaWiki `#ask` on a numeric property after the jobrunner's jobs, a Wikibase property and item with a statement, `wbsearchentities`, `{{#statements}}`, a Lua module, a formula, full-text search), the data files and `PRAGMA integrity_check`; then a restart, after which the schema update has run, the same reads pass and nothing was installed again; then a restart with `MW_AUTO_UPDATE=false`, after which no update has run and the reads pass; then read-only mode, in which the reads pass and edits and logins are refused. It passes when every check passes (each prints `ok:`), the wiki becomes healthy within 15 minutes each time, and the image installs the committed Composer lock.

## Inspections

TST-003 to TST-006 are carried out by a person, who records how each went: `skein result TST-003 pass` (or `fail`, with `--note` saying what did not hold), which writes `verification/results/recorded.toml` with who, when and the commit; it is committed like any change. A record goes stale when its procedure or a requirement it verifies changes, and `skein check` then asks for it again. Each passes when every check in it holds at the commit inspected. The requirements of parts not written yet (the offline viewer's window, its in-process serving and code, and the media store: SRS-020, SRS-024, SRS-025, SRS-027, SRS-028, SRS-045, SRS-046, SRS-061, SRS-062, SRS-073 and SRS-084) get procedures with those parts.

%procedure[TST-003 acceptance verifies=SRS-007 verifies=SRS-070 verifies=SRS-071 verifies=SRS-080 verifies=SRS-094] The wiki service's files. SRS-007: `docker-entrypoint.sh` runs every maintenance script through `maint`, which runs it as `www-data` (`as_www`), and `fix_ownership` gives the data and images volumes to `www-data` before anything else uses them. SRS-070: each variable of `.env.example` is read by `LocalSettings.php` or `docker-entrypoint.sh`, with the default `.env.example` states. SRS-071: `docker-compose.yml` defines `wiki` and `jobrunner` with the same image and both volumes, and `jobrunner` waits for `wiki` with `condition: service_healthy`. SRS-080: the `Dockerfile` builds from the official `mediawiki` image of the 1.43 line, and `MW_CONFIG_FILE` is `/etc/mediawiki/LocalSettings.php`, outside `/var/www/html`. SRS-094: the `Dockerfile` names the MediaWiki and Composer images by `@sha256:` digest; `WIKIBASE_COMMIT` is a full commit hash that the build checks after checking it out; `DEBIAN_SNAPSHOT` is a fixed time and the build fails if an apt source is not that snapshot; the image installs `composer/composer.lock`, and fails without it unless built with `COMPOSER_UPDATE=1`.

%procedure[TST-004 acceptance verifies=SRS-081 verifies=SRS-082 verifies=SRS-086 verifies=SRS-088] The offline PHP build. SRS-081: `offline/php/build.zig.zon` fetches PHP from `https://www.php.net/distributions/`, pinned by its hash; that archive's SHA-256 is the one php.net publishes for the release, and its `.asc` signature verifies with a key of the release managers php.net lists. SRS-082: every dependency of `build.zig.zon` is fetched from its publisher's official release, pinned by hash, with an entry in `offline/php/components.zig`; `build.zig` and `build/` compile each from source, and link no prebuilt library; no fetched source is committed. SRS-086: the build's default target is `x86_64-windows-gnu`, with Zig's bundled MinGW-w64, and the Build on Windows job builds it on a runner with no step installing Visual Studio or the Windows SDK. SRS-088: each GPL or LGPL component of `components.zig` (libmbfl, libbcmath) is part of a PHP extension the wiki needs, with no permissively licensed replacement, and is listed with its license in the SBOM.

%procedure[TST-005 acceptance verifies=SRS-083 verifies=SRS-089 verifies=SRS-090 verifies=SRS-092 verifies=SRS-093] A published release, on its GitHub page and in its downloaded files. SRS-089, shown: the release was published by the Release job of the CI run for its tag; it has the server zip, which holds only the files `ci.yml`'s Package job lists for it, and the Windows zip; no image was pushed to a registry. SRS-083: that run's Sign the program job passed its signature check, and on Windows the program in the zip shows a valid signature with a timestamp (`Get-AuthenticodeSignature`). SRS-090: the SBOM has every component of `components.zig`, the two images and the Wikibase commit of the `Dockerfile`, every package of `composer/composer.lock` and every line of `image/inventory.csv` at the tag, each with its version and, where its source states one, its license. SRS-092: `sha256sum -c SHA256SUMS` passes, and `gpg --verify SHA256SUMS.asc SHA256SUMS` passes with `SIGNING-KEY.asc`. SRS-093: `LICENSE` is a file of the release, and the Windows zip's `third-party-licenses` has a license text for each component of `components.zig`.

%procedure[TST-006 acceptance verifies=SRS-085 verifies=SRS-091 verifies=SRS-096] The project's records. SRS-085: the requirements are items under `docs/`, and `skein check` reports no problems (the Lint job, with the released skein). SRS-091: `LICENSE` is the MIT license, and no file the project wrote states another. SRS-096: in the CI run of a release, the Test, Build on Windows and Server jobs each uploaded results, one per check, naming the test file; the Results job's coverage counts them; and the release has `test-results.toml` and `coverage.txt`.
